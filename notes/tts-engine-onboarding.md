# TTS engine onboarding — the defined approach

**Status:** ratified pattern, owner 2026-07-25. Applies to every speech engine we
bring into the portfolio, new or revisited.

This exists because of what the 2026-07-25 direction-relay audit found: we had been
writing rich direction for four engines and **none of them ever received the voice
design**. VibeVoice reduced it to a gender regex, Dia never saw it, MOSS only got it
where one builder happened to merge it, and Qwen silently swallowed it into
`**kwargs` because `voice_description` is not a parameter of its API. Every audit
verdict recorded against those clips was, to some degree, scoring a model for
direction it was never given.

The rule that prevents a repeat: **an engine is not onboarded until we know exactly
what reaches it, and Gemma has an adapter that speaks to it in those terms.**

## The pattern

### 1. Study the engine before writing a line of pipeline code
Read the **shipped source**, not the marketing. For each engine establish:

- The literal `generate()` / processor signature — every accepted parameter.
- Which of those are *conditioning* and which are *plumbing*.
- Whether a natural-language instruction slot exists **at all**. Do not assume one
  does because the model is "controllable"; VibeVoice and Dia have none.
- How voice identity is set: instruction text, reference audio, speaker ID, or a
  random draw per seed.
- Documented vocabulary and format for any instruction slot, with real examples.
- Whether accent is a supported dimension. (So far: never, in any engine we run.)
- Decoding defaults, and whether the card warns they are sensitive.
- Licence of the **weights**, not the code repo.

Label every claim DOCUMENTED / CODE-VERIFIED / COMMUNITY / UNVERIFIED. Community
folklore has repeatedly contradicted maintainer statements.

### 2. Establish the relay matrix
Write down, per engine, which direction fields actually reach the model. Encode it
in two places so it cannot rot:

- `AI-Lab-AMD/audition/app/main.py::RELAY` — so the audition card can strike
  through direction the engine never received, and we never score a model for it.
- `scripts/synthesis/book_ingest.py::build_direction()` — the single source of
  truth for assembling each engine's payload.

### 3. Write the skill file — the Gemma adapter
One markdown file per engine at `scripts/synthesis/director_skills/<engine>.md`,
injected into the casting pass's system prompt. It must state:

- What the engine actually accepts, and what it does **not**.
- The exact format its instruction wants (Qwen: a 12-key attribute list;
  MOSS-VoiceGenerator: one free-form sentence; VibeVoice: a casting call, not a
  performance note; Dia: nothing but non-verbal tags).
- The literal words our own code parses, where casting is regex-driven.
- Known compensations (Qwen renders younger and higher than described).
- An explicit **Do not** section. Forbidding the wrong move matters as much as
  describing the right one — MOSS silently deletes anything in `[...]`, and
  VibeVoice's ambience is triggered by describing rooms.

### 4. Match the output schema to the engine
The casting pass's JSON schema is **engine-shaped**. Single-string engines are
asked for one field. Asking Qwen for two produced its whole 12-key block twice,
which duplicated the instruction and overflowed the token budget into truncated
JSON on 5 of 20 calls.

### 5. Keep line labels out of the engine pass
V/A/T and `register` describe the **line**; `voice_design` and `instruct` describe
the **engine**. These are separate director passes. When they were one call, the
training labels drifted with whichever engine Gemma was writing for — 54 distinct
register labels for 20 lines, and identical V/A/T on only 4 of 20 items. Split, it
is 20/20 on both.

`register` is a **controlled lexicon** (`register_lexicon.json`, regenerated by
`build_register_lexicon.py` from certified keeps). The director picks; it never
invents.

### 6. Smoke-render before bulk
One item, every engine, end to end, before committing to a campaign. Renderers fail
in ways banks do not predict.

### 7. Then audition
Only ever audition clips produced by a **fully fixed** pipeline for that engine.
If a fix lands mid-campaign, regenerate rather than mixing generations — the audit
record is only worth what its provenance is worth.

## Revisit list — engines graded before we knew what reached them

Source of record: [teacher-tts-audition-shortlist.md](teacher-tts-audition-shortlist.md)
(owner ears, 2026-07-17—) plus the `engine` column of ratings.csv. Every verdict
below was formed while direction was not reaching the engines as intended, so none
of them is safe as-is.

**The headline reversal — MOSS-VG.** The shortlist retired "MOSS-VG 2.1B" as
*"superseded by flagship on owner's ear"*. We now know the flagship (MOSS-TTS 8.5B)
is an **un-SFT'd base model that does not accept `instruction` at all** and reads
the prompt aloud on short lines, while MOSS-VoiceGenerator is the instruction-tuned
sibling. That retirement rests on a comparison that could not have been fair.
Reinstated 2026-07-25 as the `moss_vg` arm of `teacher-ab-v1`. Its
*anchored-instruct recipe* — always anchor age + gender + timbre before the
delivery imperative — survived as the template for every skill file we now write.

The revisit list above is the whole of the near-term work.

## The standing rule

> No TTS model enters the portfolio without a studied interface and a skill file
> adapter for Gemma. If we cannot say what reaches the model, we cannot direct it,
> and we must not grade it.
